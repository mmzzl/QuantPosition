# Feature Specification: RBAC角色继承与菜单权限联动

**Feature Branch**: `004-rbac-inheritance`
**Created**: 2026-05-14
**Status**: Draft
**Input**: 用户描述: "角色是这样的，用户可以选择角色，角色关联权限，默认有几个角色，有超级管理员，系统管理员，普通管理员，后面新增的角色可以继承这几个角色。超级管理员的角色默认有全部权限，不允许编辑，其它管理员可以勾选页面权限，勾选后，菜单里面就能展示，如果取消勾选就不允许展示。权限页面可以取消，放到角色里面，由角色进行管理。编辑的时候，需要判断当前用户是否有权限，如果没有权限则提示他不能修改"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 预设角色与权限 (Priority: P1)

系统预设超级管理员、系统管理员、普通管理员三个角色，预设角色拥有固定权限。

**Why this priority**: 预设角色是系统权限管理的基础，所有权限控制都基于这些角色。

**Independent Test**: 可以独立验证预设角色存在、固定权限分配正确、超级管理员不可编辑。

**Acceptance Scenarios**:

1. **Given** 系统初始化, **When** 系统启动, **Then** 自动创建超级管理员、系统管理员、普通管理员三个预设角色
2. **Given** 超级管理员角色, **When** 查看该角色权限, **Then** 显示全部权限且不可编辑
3. **Given** 系统管理员角色, **When** 查看该角色权限, **Then** 显示可配置的页面权限列表
4. **Given** 普通管理员角色, **When** 查看该角色权限, **Then** 显示受限的页面权限列表

---

### User Story 2 - 角色继承 (Priority: P1)

管理员可以创建新角色，新角色可以继承预设角色或其他自定义角色。

**Why this priority**: 角色继承避免重复配置权限，提升管理效率。

**Independent Test**: 可以独立验证创建继承角色、权限合并正确、继承关系正确计算。

**Acceptance Scenarios**:

1. **Given** 管理员, **When** 创建新角色并选择继承系统管理员, **Then** 新角色自动获得系统管理员的所有权限
2. **Given** 管理员, **When** 为继承角色添加额外权限, **Then** 新角色拥有继承权限+额外权限
3. **Given** 继承角色, **When** 编辑该角色, **Then** 可在继承权限基础上增加或移除权限
4. **Given** 继承链（A继承B，B继承C）, **When** 查看A的最终权限, **Then** 正确合并A、B、C的所有权限

---

### User Story 3 - 菜单权限联动 (Priority: P1)

用户看到的菜单根据其角色所勾选的页面权限动态显示。

**Why this priority**: 权限控制的核心目标是控制用户可见内容，菜单联动是用户体验的关键。

**Independent Test**: 可以独立验证角色勾选权限后对应菜单显示/隐藏、权限实时生效。

**Acceptance Scenarios**:

1. **Given** 用户拥有系统管理员角色, **When** 角色配置了"持仓管理"权限, **Then** 左侧菜单显示"持仓管理"菜单项
2. **Given** 用户拥有系统管理员角色, **When** 角色取消勾选"持仓管理"权限, **Then** 左侧菜单不显示"持仓管理"菜单项
3. **Given** 用户拥有多个角色, **When** 任一角色拥有某权限, **Then** 用户可看到对应菜单（权限合并）
4. **Given** 用户登录, **When** 用户角色权限变更, **Then** 下次登录菜单按新权限显示

---

### User Story 4 - 权限编辑控制 (Priority: P1)

编辑角色时，系统判断当前用户是否有权限修改，无权限则拒绝并提示。

**Why this priority**: 权限边界控制是安全基础，防止低权限用户越权修改。

**Independent Test**: 可以独立验证权限验证逻辑正确、拒绝访问提示清晰、无权限用户无法修改高权限角色。

**Acceptance Scenarios**:

1. **Given** 当前用户是普通管理员, **When** 尝试编辑超级管理员角色, **Then** 系统拒绝并提示"无权限修改此角色"
2. **Given** 当前用户是系统管理员, **When** 尝试编辑超级管理员角色, **Then** 系统拒绝并提示"无权限修改此角色"
3. **Given** 当前用户是系统管理员, **When** 尝试编辑普通管理员角色, **Then** 允许编辑
4. **Given** 当前用户是超级管理员, **When** 尝试编辑任何角色, **Then** 允许编辑

---

### User Story 5 - 角色权限管理界面 (Priority: P2)

管理员通过角色管理界面统一管理角色和权限，不再有独立的权限管理页面。

**Why this priority**: 简化管理复杂度，将权限管理内聚到角色管理中。

**Independent Test**: 可以独立验证角色管理界面功能完整、权限勾选交互流畅。

**Acceptance Scenarios**:

1. **Given** 管理员, **When** 进入角色管理页面, **Then** 显示角色列表和每个角色的权限勾选
2. **Given** 管理员, **When** 创建新角色, **Then** 可选择继承角色并勾选页面权限
3. **Given** 管理员, **When** 编辑角色, **Then** 可修改角色名称、继承关系、权限勾选
4. **Given** 管理员, **When** 删除自定义角色, **Then** 角色被删除，用户自动解除角色绑定

---

### Edge Cases

- 角色继承循环检测：A继承B，B继承A，应该禁止并提示错误
- 删除被继承的角色：需要处理继承链，可能需要阻止删除或级联调整
- 权限冲突：子角色移除继承来的某个权限，需要正确处理
- 最后一个管理员角色：防止所有用户都无法访问管理功能
- 超级管理员角色删除：应禁止删除预设的超级管理员角色

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须预设超级管理员、系统管理员、普通管理员三个角色
- **FR-002**: 超级管理员角色必须拥有全部权限且不可编辑
- **FR-003**: 系统必须支持角色继承关系配置
- **FR-004**: 角色必须关联页面级权限（菜单权限）
- **FR-005**: 用户看到的菜单必须根据其角色权限动态显示
- **FR-006**: 编辑角色时必须验证当前用户权限，无权限则拒绝
- **FR-007**: 系统必须支持继承链权限合并计算
- **FR-008**: 必须防止角色继承循环
- **FR-009**: 删除被其他角色继承的角色时必须处理继承关系
- **FR-010**: 权限管理集成到角色管理界面中，不再独立存在

### Key Entities *(include if feature involves data)*

- **Role**: 角色实体，包含角色名、角色类型（预设/自定义）、继承角色列表、直接权限列表
- **Permission**: 页面级权限实体，包含权限标识、权限名称、关联菜单路径
- **RoleInheritance**: 角色继承关系（角色A继承角色B）
- **User**: 用户实体（已有），关联角色列表

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 预设角色在系统首次启动时自动创建
- **SC-002**: 超级管理员角色不可编辑（所有字段禁用）
- **SC-003**: 角色编辑时权限验证在100毫秒内完成
- **SC-004**: 菜单根据用户权限动态显示，权限变更后下次登录生效
- **SC-005**: 继承链支持最多5层深度
- **SC-006**: 无权限用户编辑角色时收到明确错误提示

## Assumptions

- 系统已有用户、角色基本数据模型
- 菜单路径与权限标识已建立映射关系
- 预设角色在系统初始化时创建
- 继承关系存储在角色实体内（非单独关系表）
